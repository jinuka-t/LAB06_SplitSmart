# Detailed design proposal

All interfaces and defaults here are proposals, not approved requirements. Baseline and authority: [architecture](architecture.md#baseline-and-independence). Decision identifiers refer to [decisions](decisions.md).

## Accounts and permissions

IdentityService normalizes email using one documented conservative comparison rule (trim and case-insensitive comparison, provisional D07), hashes passwords using an adaptive salted password-hash adapter, and persists only token digests. Password length, hash parameters, session lifetime, token lifetime and rate limits need security review. Register creates UNVERIFIED account plus verification-delivery outbox record; only token redemption changes it to VERIFIED. Login requires VERIFIED and a valid password, returns an opaque expiring session. Recovery request always returns the same public response to avoid account discovery; reset consumes a single-use, expiring token and revokes sessions. Concurrent token consumption must update one unconsumed record atomically. Tokens and passwords never appear in logs or group DTOs. Mail failures are retried and observable; no fake verification bypass in a release.

| Actor | Allowed | Restrictions |
|---|---|---|
| Unauthenticated caller | register, verify, login, request/complete recovery | rate limited; no financial/group access |
| Verified account | own profile; create group; view/accept invitation addressed to verified email | invitation alone grants no group access |
| Active MEMBER | group expense/status/receipt, pairwise balances, group financial reports, submit expense | no other account credentials/profile secrets; group financial data is shared by accepted membership |
| Active MANAGER | member rights plus invite/remove/promote, policy management | cannot bypass invitation acceptance or erase history |
| Current stage approver | approve/reject pending expense per frozen policy | must remain active; default cannot approve own submission |
| Payment sender | record settlement of their own debt to a historical/active group counterparty | no manager/recipient impersonation of sender, pending product review D05 |
| Notification recipient | list/read own notifications | group links and receipts recheck membership |

Every object access checks group ownership and permission at service time; caller-supplied account IDs do not establish identity. Return NOT_FOUND for inaccessible object IDs; use FORBIDDEN for a known permitted resource with a prohibited operation. Former members retain account access but provisionally lose direct group access. Managers can still see and reconcile their retained balances; re-invitation/acceptance restores sender settlement access. Do not remove a debtor without warning about this limitation. Departed-member self-service historical access is an open product decision (D05), not an implied waiver of history retention. Receipt downloads use the same current group permission as expense reads.

## Group and membership workflow

Group creation atomically creates group, creator's active MANAGER membership and an initial one-stage policy with no eligible reviewer, marked NOT_READY. The manager configures an explicit eligible reviewer after another member accepts. A one-person group may exist; submission is blocked until eligible review exists. An unready initial policy is the only exception to the configured-policy nonempty eligibility constraint. Invitation is PENDING -> ACCEPTED, DECLINED, REVOKED or EXPIRED; only target verified account can accept. Acceptance atomically establishes/reactivates one membership. Membership is ACTIVE -> REMOVED; repeated removal is safe. Last manager removal is rejected. Managers may promote another active member. Removal preserves all references and never deletes financial history.

Group policy selects ordered stages, explicit eligible member IDs and a required distinct approval count for each stage. MVP allows exactly one stage and one approval; full product permits multiple stages/counts. Manager authorization is not implicit approval eligibility. Submitter self-approval is false by default; a policy may explicitly enable it, subject to product review. Validate eligibility again per submitted expense after excluding submitter; no eligible approver -> POLICY_NOT_READY, no expense. Snapshot policy version/stages/members with submission. Later policy edits affect new submissions only. If removal makes a pending snapshot impossible, mark it operationally BLOCKED (still PENDING financially), show manager/submitter why, and allow submitter withdrawal and a new linked submission with a current policy. An active eligible current-stage approver may still reject a blocked expense; blocked readiness prevents approval progress, not authorized rejection. No silent replacement or automatic approval of old decisions. Blocked is a computed review condition, not a financial state.

## Expense lifecycle and exact approval

ExpenseService accepts independent payer ID, ordered unique participants, positive Money, LocalDate, nonblank description, split mode, percentages and optional staged receipt. Submitter, payer and participants must be active in that group at submission. Payer can be absent from participants. Preserve order even when payer is included; never sort participants by ID for allocation. Allocate and persist exact immutable shares before creating PENDING expense, frozen policy and notification outbox in one transaction. Invalid input creates no approvable expense.

States: PENDING -> APPROVED, REJECTED or WITHDRAWN. APPROVED/REJECTED/WITHDRAWN are terminal; no in-place edits/deletes. A corrected rejected/withdrawn expense is a new expense linked by supersedesExpenseId, with new shares, review and notifications. Approved corrections/voids are outside this proposed release and require a future audited reversal design; no mutation may silently alter posted balances.

ApprovalService locks group financial row and expense, rechecks the operation key under lock, checks expectedVersion, state, current active membership, snapshot stage and eligibility. Record one decision per expense/stage/actor. Reject at current stage immediately makes REJECTED, without ledger entries. Approve adds decision; until stage quorum met remain PENDING; advance only in stage order. Distinct reviewers required within stage; same reviewer may serve later stages if explicitly selected (D02). On final approval, atomically set APPROVED, append one ledger entry per nonpayer positive share, update pair projections, and store idempotent response. Database unique expense-posting keys prevent duplicate financial effect, including zero-debt expenses where no entries exist: a unique finalization record still exists. Failure rolls back decisions, status, finalization, postings, projection and response together. Concurrent reject/approve is serialized; first committed terminal result wins and the other receives STATE_CONFLICT. Stale expectedVersion returns VERSION_CONFLICT, with no decision. A retry with the same request key retrieves original result before rechecking version.

Membership removal uses the same group lock as approval and submission so it cannot race the eligibility check. Participants removed after submission retain immutable shares. Payer removal does not invalidate historical financial entitlement. Only approver removal can block further approvals. Authorization of an existing request-key replay is rechecked against current read access before returning private response data.

## Balances and recorded settlements

BalanceService derives signed debt for each unordered member pair within one group/currency, retaining all contributing expense/payment events. Reciprocal approved obligations net within that pair only (D05). No self pair, no cross-group netting. API presents a positive amount with explicit debtor and creditor, or zero with canonical pair IDs. All group pairs can be requested; omitted pairs have zero and diagonal is always zero. Historical removed members remain listed where financial records exist.

SettlementService is a record of an external payment, not execution of a bank transfer. Sender must be the authenticated active member and net debtor, recipient a different retained group member. Positive, exact-unit amount cannot exceed current net debt. Lock group financial row, recheck the operation key under lock, read pair projection, validate, append immutable Payment and settlement ledger entry, update projection, and save idempotent result in one transaction. If two payments compete for the same outstanding amount, second re-evaluates after first commits; overpayment is rejected. Unique actor/key prevents duplicate payment after a lost response. Payment history remains visible even if the pair returns to zero or reverses later. Date is user-entered LocalDate; recordedAt and commit sequence are server-controlled audit fields. Backdating does not bypass current-debt validation and can produce historically negative report balances; label these as as-of reconstructions, not past validation states. Reversal/edit of a payment needs a separate audited future operation, not deletion.

## Notifications and receipt failure boundaries

FR-008 unconditionally requires notifying all group members except submitter; AC-008 is conditioned on enablement. Proposed D04 default: always create in-product notifications for the active-member audience captured at submission, excluding submitter. This does not resolve whether an off switch is permitted. No optional email preference suppresses in-product records pending that decision. Identity verification/recovery mail is a separate security delivery channel.

Submission commits an outbox event; worker retries delivery to per-recipient inbox with unique (expense,recipient,event type), with exponential backoff, jitter, attempt count, last error and operational dead-letter status after a provisional cap. Notification availability is eventually consistent and is not evidence of approval. Failed notification never reverses submitted expense or posts balances. Inbox is durable; read/unread changes only on recipient action. Removed recipients cannot follow a group link; worker rechecks active membership before publishing sensitive text and suppresses unsafe delivery with an auditable reason. Product must define whether removal after submission changes the original audience guarantee. Do not promise exactly-once external email delivery; inbox uniqueness gives one logical alert. Retry/dead-letter SLA, channels and monitoring ownership remain open.

ReceiptService stages a private image upload for the caller/group, validates actual image content, configured MIME/byte/pixel limits and safe decoding. Proposed initial limits: JPEG/PNG, 10 MiB and 25 megapixels (D07). Upload is not public. Submission consumes a staged token owned by submitter in same group; expired/unready upload fails before expense creation. Blob must be durably present before SQL attachment. An orphan blob after SQL failure is garbage-collected after TTL; attached bytes are never collected by staging cleanup. Store digest and length to detect missing/corrupt bytes. Receipt access failure returns RECEIPT_UNAVAILABLE and records an operational incident, leaving expense and ledger intact. Backup/restore retains SQL and attached blobs. No receipt is necessary to approve a valid expense.

## Reports and disconnected clients

ReportService uses one database snapshot and commit watermark. Three sections: approved expense/share totals, payment totals/history, and signed pair opening/movement/closing balances. Default dates unbounded; specified start/end are inclusive LocalDates. Expense activity uses expenseDate, payments use paymentDate; approval status is current at snapshot. Approval recorded later may therefore change a historical date report; include generatedAt, ledger watermark and this basis in output. Start=end means one day; start>end is INVALID_DATE_RANGE; no matches yields empty rows and zero activity, not an error.

Group filter is mandatory for MVP; member filter restricts expense rows to payer/participant, includes only that member's shares/obligations in financial subtotals, payments to sender/recipient and balances to incident pairs. Group-wide expense gross amount is shown separately from member share total so a payer's whole expense is not confused with their debt. For member reports opening/closing include only incident ledger edges, not unrelated participants' shares. No multi-currency sum. Expense status filter can expose pending/rejected detail but financial totals always use APPROVED only. Receipt contents, passwords, tokens and other groups' records are never report fields. Optional criteria not listed in contracts are rejected.

Opening balances include matching pair ledger activity before start; period movement includes only matching events in range; closing = opening + movement. Opening is explicitly labelled carry-in, not part of period totals, to preserve FR-016. Unbounded start means zero opening. End unbounded uses snapshot end. Commit watermark prevents mixing separately read revisions; clients refresh all related views at or after saved watermark. A replica must catch up or query primary before acknowledging read-after-write completion.

Offline MVP permits unsaved local screen input only. Disable financial submission and do not show completion offline. A timeout means outcome unknown: retry same operation/key or query own operation status; never generate a new key automatically. No offline credential/token or receipt cache is proposed. Future clients must share these completion and currency rules.
